# Canonical Demonstration Dataset

Generated by mini-phase **P9.1 — Canonical Demonstration Dataset**.
This is the permanent teaching/demo baseline for FBMS: a large,
realistic-looking body of historical `FeedbackSession`/`FeedbackAnswer`
records layered on top of the existing seeded Departments, Locations,
Tablets, Surveys, and Users — none of which were changed to produce it.

## At a glance

| | |
|---|---|
| Sessions generated | 3,000 |
| Answers generated | 10,671 |
| Date range | 2026-03-01 through 2026-08-08 (161 days) |
| Reference codes | `FB-2026-000011` through `FB-2026-003010` |
| Departments covered | Registrar, Library (the only two that exist) |
| Tablets used | All 4 existing seeded tablets (`REG-TAB-01`, `REG-TAB-02`, `LIB-TAB-01`, `LIB-TAB-02`) |
| Surveys used | The 2 currently-published surveys only (see Limitations) |
| Generation method | Deterministic (see `GENERATION_PARAMETERS.md`) |

These 3,000 sessions are **in addition to** the 10 sample sessions
`backend/src/seeders/feedbackSeeder.js` already seeds as part of the
standard `npm run seed` (reference codes `FB-2026-000001`–
`FB-2026-000010`) — that seeder is unchanged, still runs as before,
and is still what the backend test suite exercises. After running both,
the development database has 3,010 total feedback sessions.

## Entity mapping

Every session in this dataset references an existing entity by its
business key, exactly like `feedbackSeeder.js` already does — no new
Survey, Tablet, Location, or Department was created:

- **Tablets** — the 4 seeded by `tabletSeeder.js`: `REG-TAB-01`/`REG-TAB-02`
  (Registrar Main Counter / Records Room) and `LIB-TAB-01`/`LIB-TAB-02`
  (Library Circulation Desk / Reading Hall).
- **Surveys** — the 2 currently-published surveys seeded by
  `surveySeeder.js`: **"General Service Feedback"** (Global) and
  **"Registrar Office Feedback"** (Registrar department).
- **Departments/Locations** — derived from each session's tablet, the
  same way the real `POST /api/v1/mobile/feedback` endpoint derives
  them (never invented, never taken from the survey).

## Which survey each tablet's feedback belongs to (and why)

This is the one place this dataset deliberately deviates from
`feedbackSeeder.js`'s own 10 hand-written sample sessions, and it's
worth calling out explicitly:

`backend/src/services/mobileService.js`'s `resolveActiveSurveyForTablet`
— the real function a tablet uses to determine which survey it can
currently submit against — resolves in strict **Location → Department
→ Global** precedence, considering only currently-published,
non-archived surveys. Given the current seeded state:

- **Registrar tablets** (`REG-TAB-01`, `REG-TAB-02`): the Registrar
  *department* survey ("Registrar Office Feedback") is published, so it
  always wins over the Global survey. **Every Registrar-tablet session
  in this dataset uses "Registrar Office Feedback."**
- **Library tablets** (`LIB-TAB-01`, `LIB-TAB-02`): the Library
  *department* survey ("Library Services Feedback") exists but was
  seeded as a **draft** (`isPublished: false`) — a real tablet could
  never have resolved or submitted against it. Resolution therefore
  falls through to the Global survey. **Every Library-tablet session in
  this dataset uses "General Service Feedback."**

`feedbackSeeder.js`'s own 10 sample sessions don't follow this rule for
Registrar tablets (6 of its 10 sessions tag `REG-TAB-01`/`02` with the
Global survey even though the Registrar survey was already published at
seed time) — that's fine for a small hand-written illustrative fixture,
but this phase's explicit instruction was to generate only data
**supported by the current implementation**, so the 3,000-session
generator follows the real resolution rule strictly rather than
reproducing that inconsistency at scale.

## Documented limitation

Per this phase's own instruction ("If realism would normally require
more ... document the limitation instead of changing the
architecture"): because "Library Services Feedback" remains an
unpublished draft, this dataset contains **zero** feedback against it,
and Library tablets only ever appear against the Global survey. If a
future phase publishes the Library survey, newly-generated historical
data could be given a mixed Library-survey/Global-survey split for
Library tablets — this generator was deliberately not changed to
manufacture that mix now, since doing so would mean inventing
submissions no real tablet could have made under the survey's actual
(draft) state at any point in this dataset's date range.

## Known, expected characteristic: tablets show "Offline" in Live Monitoring

This dataset only writes `FeedbackSession`/`FeedbackAnswer` records — it
never touches `Tablet.lastSeen` (that field is only ever updated by a
real `POST /api/v1/mobile/heartbeat` call, per `docs/DATA_MODEL.md`).
Live Monitoring's Online/Offline/Inactive status is computed from
`lastSeen` recency, so all 4 tablets will correctly show **Offline**
until a real or simulated heartbeat occurs. This is expected, not a
defect — Live Monitoring's own historical Feedback Count/Last Feedback
columns (which this dataset does populate) still work correctly.

## Authentication — unchanged

No new login account was created, no seeded user was replaced or
modified, and no role/permission was changed. See
`LOGIN_CREDENTIALS.md` for the existing 9 seeded accounts, which remain
the only way to sign in to the Admin Web application.
